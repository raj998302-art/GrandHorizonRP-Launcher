# GUEST PERSISTENCE CONTRACT (implemented)

## 1. The bug (before)

Device flow worked (Guest -> character created -> played) but on every app
restart the launcher showed character creation again.

**Root cause:** `confirmCharacter()` only logged a JSON line — no session was
persisted anywhere (no SharedPreferences, no file, no backend call). The guest
identity from the WebView (`front_token`, TTL 12 h) was held in a Java field and
died with the process. There was also no server-side record that a character
choice had been made.

## 2. The contract (after)

### 2.1 Server side (authoritative) — ghrp-auth (Vercel) + LemmeHost MySQL

Endpoints (live, verified end-to-end this session):

| Endpoint | Purpose |
|---|---|
| `POST /api/v2/auth/token {grant_type:"guest"}` | create guest account in the SA-MP `accounts` table; returns `front_token` + **`guest_secret`** (once) |
| `POST /api/v2/auth/token {grant_type:"password"}` | re-auth for guest restore (email + guest_secret) or normal sign-in |
| `GET /api/v2/character` (Bearer front/access token) | `{has_character, character:{name, sex, sex_id, skin}}` |
| `POST /api/v2/character {sex, skin}` (Bearer) | saves `accounts.sex`, `accounts.skin`, sets `launcher_char_created=1` |

Schema (additive migration on the production DB, existing data preserved):

```sql
ALTER TABLE accounts ADD COLUMN launcher_char_created TINYINT NOT NULL DEFAULT 0;
-- executed 2026-02 (sandbox, verified: all 64 tables intact, accounts untouched)
```

The character lives **in the game database the SA-MP gamemode reads** — the same
accounts row the gamemode uses at login (`SetPlayerSkin(playerid, accounts.skin)`).
There is **no second character database**.

### 2.2 Device side — SessionStore (`session.json`, app-private `getFilesDir()`)

```json
{
  "schema": 1,
  "kind": "guest" | "user",
  "email": "guest_...@guest.ghrp.local",
  "guest_secret": "<random hex — guest accounts only>",
  "front_token": "<last valid SSO token>",
  "account_name": "Trevor_Vance",
  "account_uuid": "acc-15",
  "saved_at": 1739923706242
}
```

- Atomic write (tmp + rename); schema version gate.
- **Registered users' passwords are never stored.** Only the guest secret (a
  random throwaway generated by the backend for this device) is kept, because a
  guest cannot re-login any other way.
- No tokens/secrets are logged (log lines carry kind/name only).

### 2.3 Restore algorithm (MainActivity.runRestore)

1. `SessionStore.load()` — no session -> WebView auth.
2. Guest with secret -> password grant -> fresh `front_token` (persisted).
3. User -> stored `front_token` used directly.
4. `GET /api/v2/character`:
   - `has_character=true` -> CHARACTER_READY (skip creation, straight to server select)
   - `has_character=false` -> CHARACTER_REQUIRED (creation, once)
   - `401/403/404` -> identity invalid on the server -> clear + WebView auth
   - network error -> retry panel (session NOT dropped)

### 2.4 Skin id mapping (honest scope)

The native preview renders the real BR `.mod` meshes from the game data. The id
saved to `accounts.skin` is a **standard SA-MP ped id** chosen from a documented
per-gender table (`male {26,7,46,60,72,0,170,66}`, `female {12,13,40,55,90,192,91,216}`)
— every id is a valid SA-MP skin. The preview-mesh ↔ SA-MP-ped visual mapping
becomes exact when the world/multiplayer milestone lands (networked players are
skinned by the server). The gamemode's own registration dialogs remain the
final authority for gameplay looks.

- POST character (female/12) -> `has_character:true, saved:true`
- re-auth with guest_secret -> fresh token
- GET character with fresh token -> character restored ✔
